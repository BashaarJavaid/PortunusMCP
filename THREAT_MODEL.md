# Threat Model

What PortunusMCP protects against, what it explicitly does not, and the assumptions the whole model depends on. See [`ARCHITECTURE.md`](./ARCHITECTURE.md) for how each protection is implemented, and [`docs/adr/`](./docs/adr/) for why certain alternative approaches weren't used.

---

An explicit scope boundary is worth more to a technical reviewer than an implied claim of total coverage.

| Threat | Protected? | Notes |
|---|---|---|
| Tool Poisoning (adversarial text in tool descriptions) | **Enforce: Partial; Observe: weaker advisory detection** | In `enforce`, a changed description blocks (`DENY_DRIFT`) until re-approval; first-contact heuristics only flag and raise risk. In `observe`, both drift blocking and risk outcomes are advisory and the call is forwarded. Descriptions reach the LLM **verbatim** in both modes, and novel phrasing evades pattern lists |
| Rogue / rug-pulling MCP server (schema/shape mutation) | **Enforce: Yes; Observe: detects and audits** | Drift Detector classifies mutations in both modes; High/Critical blocks `tools/call` until re-approval only in `enforce`. Observe records the would-be `DENY_DRIFT` and forwards |
| Compromised registered upstream reading gateway enforcement secrets | **Yes (scoped)** | Each session's upstream runs in a hardened container with a minimal allowlisted environment, read-only root, non-root UID, dropped capabilities, bounded resources, and no network by default. It receives neither the audit private key/secrets directory nor the Docker socket, Redis/Postgres credentials, signing secrets, or TOTP secrets (`tests/integration/test_upstream_isolation.py`). This does not cover a compromised Docker host or gateway container |
| DNS rebinding against the Streamable HTTP edge | **Yes (scoped)** | The installed MCP SDK's Host/Origin validator runs on every `/mcp/*` request before authentication, body parsing, or session creation. Host and any supplied Origin must match `ALLOWED_HOSTS` / `ALLOWED_ORIGINS` (`tests/integration/test_resource_limits.py`); missing Origin remains valid for stock non-browser clients. The guarantee is scoped to correct deployment allowlists and does not replace TLS or ingress configuration |
| Authenticated resource exhaustion or stuck upstream tools | **Partial** | The edge bounds body bytes and JSON depth; the single-replica Session Manager separately caps sessions and outstanding calls per identity; Redis enforces a per-identity fixed-window `tools/call` rate; and a 60-second end-to-end deadline reaps the whole session while an in-flight heartbeat prevents premature idle cleanup (`tests/integration/test_resource_limits.py`). Multiple valid identities can still exhaust host/container capacity, a fixed window permits a boundary burst, and terminating a session cannot undo an upstream side effect that already started |
| Unauthenticated credential stuffing / auth-path availability | **Partial** | Wrong bearer keys, unknown signed key ids, and bad signatures share an exact-source Redis window across MCP/admin authentication; the sixth failure receives 429, later presented credentials stay blocked for the fixed window, and every block feeds an immediate warning alert (`tests/integration/test_risk_telemetry.py`, `tests/adversarial/test_signed_auth.py`). Uvicorn accepts the client address only from configured trusted proxies. IP rotation, an initial concurrent burst, and shared-NAT collateral remain; source throttling cannot identify one attacker behind many addresses |
| Unauthorized tool access by a known identity | **Enforce: Yes; Observe: No, audit-only** | RBAC + ABAC are binding only in `enforce`; observe records the earliest would-be denial and forwards |
| Overly broad or contextually risky calls by an authorized identity | **Enforce: Yes; Observe: advisory** | Risk scoring and factors run in both modes; challenge, approval, and deny bands stop calls only in `enforce` |
| Replay of a captured request | **Enforce: Yes for `signed` identities / Partial for `bearer`; Observe: detects only** | In `enforce`, signed request HMAC plus nonce dedup prevents byte-identical replay and fresh-nonce forgery; bearer dedup remains opportunistic. In `observe`, nonce checks still consume and detect duplicates but `DENY_REPLAY` is audited and forwarded. Signature failures remain HTTP 401 in both modes |
| Prompt injection reaching the LLM through tool *results* (not descriptions) | Partial | Out of scope for a protocol-layer gateway — this needs to be handled by the client/agent framework itself; the gateway can log and rate-limit but cannot semantically evaluate result content |
| Stolen API key | Partial | Source-scoped authentication throttling remains enforcing in both modes; anomaly/risk-based blocking applies only in `enforce`. The gateway cannot distinguish a stolen bearer key from its holder. `signed` identities keep credentials off the wire |
| Compromised host OS running the gateway itself | No | If the host is compromised, the attacker has the signing key and Redis/Postgres access; this is a deployment/infra hardening problem (secrets management, host patching), not something the application layer can defend against |
| Malicious local user with shell access to the gateway container | **No** | The mounted Docker socket is root-equivalent access to the Docker host. The socket is required to launch isolated upstreams, so a gateway shell can create privileged containers or inspect other workloads; container flags do not preserve a boundary after that compromise |
| Insider admin abusing legitimate admin-API access (policy edits, drift approvals) | No | The audit log makes such actions attributable and tamper-evident after the fact, but does not *prevent* an admin with legitimate credentials from making a bad change — that requires a separate approval workflow (e.g. two-person policy activation), which is out of scope for this project. **Phase 4 includes a documented design for two-person policy activation** (an approval workflow required before a policy change takes effect), which closes this gap as an administrative overlay rather than a core gateway logic change — the gap is recognized and has a planned path to closing it, even though it isn't built in v1. |

**Assumptions** — every threat model implicitly relies on some things being true; stating them explicitly is what separates a scoped security document from an implied claim of total coverage:

- The production gateway stays loopback-bound behind an operator-managed TLS reverse proxy; `FORWARDED_ALLOW_IPS` names only that proxy's IP/CIDR and the proxy overwrites forwarded client headers. The gateway does not defend against a broken or misconfigured termination point. Gateway/Postgres/Redis traffic is plaintext on the isolated single-host backend network, which is part of the trusted deployment boundary.
- Remote operator CLI traffic uses that HTTPS termination point. Plain HTTP is accepted by the CLI only for loopback development, and the admin bearer key is supplied through `PORTUNUSMCP_ADMIN_KEY`, not a command-line argument.
- The gateway host is not already compromised at deployment time (a compromised host invalidates the signing-key and credential guarantees entirely — see the threat table above).
- The operator-owned policy and audit-key directories are durable, writable by gateway UID 1000, and backed up together with Postgres. Crash recovery assumes their atomic rename/fsync semantics; archived fingerprint-named public keys are retained for as long as any audit row may reference them. The verifier receives only the public-key subdirectory.
- The operator controls the local Docker daemon and approves each upstream image reference and container specification in the versioned policy. Production Compose services and production policy upstreams use immutable image digests. Runtime pulling is disabled, so the gateway never silently fetches a replacement.
- Production runs exactly one gateway replica. Session/container handles are process-local and two audit writers can fork the chain; Redis/Postgres do not make horizontal scaling safe.
- Redis is a trusted, password-protected component on the internal deployment network. Production AOF reduces routine restart loss but is not a zero-loss durability guarantee.
- Postgres is trusted to execute the queries it's given faithfully — PortunusMCP defends against *external* tampering with stored rows (via the hash chain and signatures), not against a malicious database engine or a superuser with direct `UPDATE` access bypassing the application entirely (covered under "insider admin," above).
- The `mcp` SDK's own JSON-RPC framing is trusted to be spec-compliant; PortunusMCP does not re-implement wire-level protocol conformance checking beyond what it needs for interception.
- **Multiple upstreams are registered per policy (`servers:` block, items 35/39).** Each entry is a typed container specification; clients connect to `/mcp/<server_id>` and one session is bound to one isolated container at connect time. RBAC grants, drift baselines, schema caches, risk frequency/decay counters, approvals, and runtime fingerprints are keyed on the real `server_id`. Registration is still the trust decision: every registered server gets the same pipeline and thresholds; per-server trust tiers remain a discussion (`ARCHITECTURE.md` §4.7), not a capability.
